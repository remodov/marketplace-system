# Шаг 7. Тот же каталог, но по-взрослому

## Сначала — сравнить

Перед кодом сделай упражнение на чтение. Открой рядом два сервиса:
`services/catalog-starter` (шаги 1–6) и `services/catalog` (этот). Поведение у них
почти одно и то же, а устройство разное:

| | starter | catalog |
|---|---|---|
| слои | контроллер → сервис → репозиторий | контроллер → UseCase + Handler → порт → адаптер |
| контракт | пишется руками в контроллере | OpenAPI, DTO и интерфейс генерируются |
| доступ к базе | Spring Data JPA | jOOQ по сгенерированной из схемы модели |
| правила | внутри сущности | в Handler и в доменных типах |
| доступ | нет | ABAC: владелец или админ, чужое — 404 |
| журнал | нет | действия админа пишутся в аудит |

Ответь себе на два вопроса и запиши ответы — их разберём на созвоне:
**что эта сложность дала** и **чего она стоила**. Обе части обязательны: сказать
«так правильнее» — не ответ.

## Что нужно сделать

Перенести свой третий шаг — смену цены — во взрослый каталог, по здешним правилам:

```
PATCH /api/v1/products/{productId}/price    {"price": 79990.00}
```

Порядок работы обратный привычному: сначала контракт, потом код.

1. **Контракт.** Опиши ручку и схему тела в `src/main/resources/openapi/catalog.openapi.yaml`.
   Сборка сгенерирует DTO и метод в интерфейсе `ProductsApi`.
2. **UseCase.** Запись-команда со всем, что нужно для выполнения: какой товар,
   кто просит, админ ли он, какая цена. Посмотри на `PublishProductUseCase`.
3. **Handler.** Само правило: цена больше нуля, товар существует, чужой товар для
   не-админа выглядит как несуществующий (404, не 403 — иначе по кодам ответа
   можно перебрать чужие карточки). Действие админа пишется в аудит с действием
   `AuditLogger.ACTION_PRODUCT_PRICE_CHANGED`.
4. **Порт и адаптер.** Метод обновления цены в `ProductRepository` и его
   реализация на jOOQ.
5. **Контроллер.** Реализуй сгенерированный метод: собрать use case, отдать
   диспетчеру, вернуть результат. Правил здесь быть не должно.

## Как проверить себя

Взрослому сервису нужна настоящая база: тесты идут не на H2, а на PostgreSQL из
стенда, и схему для них накатывает Liquibase, а классы jOOQ генерируются из неё.

```bash
docker compose -f ../../infra/compose.yaml up -d postgres-catalog
../../gradlew :catalog:test
```

Красный `ChangeProductPriceIntegrationTest` — шесть проверок: владелец меняет
цену, цена уезжает в базу, ноль не проходит, чужой товар даёт 404, неизвестный
товар даёт 404, админ меняет и оставляет след в журнале.

## На что посмотреть по дороге

- Цена проверяется дважды: схемой контракта (`exclusiveMinimum`) и в handler'е.
  Тест на нулевую цену видит ответ от валидации контракта — до use case запрос не
  доходит. Зачем тогда проверка внутри? Потому что use case вызывают не только
  из HTTP, а правило не должно зависеть от того, кто его позвал.
- Чужой товар отдаёт 404, а не 403 — сравни с 403 в ответе на запрос без токена
  и подумай, почему коды разные.
- `FOR_UPDATE` при чтении товара — это то же, что ты делал в пятом шаге, только
  выраженное через порт репозитория.
- Сравни объём работы: в starter та же смена цены заняла три файла, здесь — пять
  плюс контракт. Это и есть цена, которую ты только что назвал в ответе выше.
