# Шаг 2. Фильтр каталога по цене

## Что нужно сделать

Ручка `GET /products` умеет отдавать весь каталог и искать по названию.
Добавь необязательный параметр `maxPrice`:

```
GET /products?maxPrice=2000
```

С ним ручка отдаёт только товары не дороже указанной цены, отсортированные
по возрастанию цены. Без параметра поведение прежнее — весь каталог.

## Где править

Три файла, в каждом стоит `// TODO шаг 2`:

| файл | что там сделать |
|---|---|
| `ProductRepository` | объявить метод выборки — запрос Spring Data выведет из его имени |
| `ProductService` | сценарий чтения, с правильной границей транзакции |
| `ProductController` | необязательный параметр и выбор сценария |

SQL писать не нужно ни строчки: имя метода репозитория — это и есть запрос.
Подсказка по неймингу: `findBy` + поле + условие + `OrderBy` + поле + направление.

## Как проверить себя

```bash
../../gradlew :catalog-starter:test
```

Тест `ProductPriceFilterTest` красный — четыре проверки: фильтр отсекает лишнее,
дешёвое идёт первым, граница включается (товар ровно за `maxPrice` попадает
в выдачу), и запрос без параметра по-прежнему отдаёт весь каталог. Задание
сделано, когда зелёные все четыре и не сломались пять из `ProductApiTest`.

## На что посмотреть по дороге

- Почему у метода чтения `@Transactional(readOnly = true)`, а не просто `@Transactional`.
- Что уходит в базу: включи `spring.jpa.show-sql: true` и посмотри на SQL, который
  Spring Data собрал из имени метода.
- Граница `<=` против `<` — в требовании написано «не дороже», это включающее условие.
  Тест на границу существует именно потому, что здесь легко ошибиться на единицу.
