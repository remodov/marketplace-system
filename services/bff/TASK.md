# Шаг 13. Граница системы: экран и лимит частоты

## Что нужно сделать

Мобильный клиент показывает экран заказа: статус, товары с картинками и
названиями, состояние платежа. Данные лежат в трёх сервисах. Если клиент пойдёт
за ними сам, он заплатит тремя круговыми задержками — на плохой сети это
секунды.

BFF решает это за него: одна ручка, внутри — походы к соседям.

**1. Сборка экрана.** `OrderScreenService.assemble`: заказ уже прочитан, из него
известны товары. Нужно добрать карточки товаров и статус платежа. Эти два похода
независимы — экран не обязан ждать их по очереди.

**2. Лимит частоты.** `RateLimiter.check`: считаем запросы клиента в текущем
окне. Счётчик живёт в Redis, а не в памяти процесса: инстансов границы
несколько, и лимит должен быть общим, иначе он тихо умножается на их число.
Ключ должен протухать сам вместе с окном — отдельной чистки быть не должно.
При превышении фильтр отдаёт 429 и `Retry-After` (это уже написано).

```bash
docker compose -f ../../infra/compose.yaml up -d redis

```

Красные: `OrderScreenIntegrationTest` (экран собирается из трёх заглушек;
отсутствие платежа экран не ломает) и `RateLimitIntegrationTest` (четвёртый
запрос за минуту получает 429; соседний клиент чужую квоту не расходует).

Redis нужен настоящий — в этом весь смысл: счётчик общий.

## На что посмотреть по дороге

- Что делать, если платежа ещё нет: заказ не оплачивали, и это нормальное
  состояние экрана, а не ошибка. Сравни с ситуацией «сервис платежей лежит» —
  ответы клиенту должны быть разными.
- Почему лимит считается по идентификатору клиента, а не по IP: за одним адресом
  сидит целый офис и мобильный оператор.
- Окно на минуту с фиксированной границей — самый простой вариант, и у него есть
  известный изъян: на стыке двух окон можно пройти вдвое больше. Найди этот
  сценарий и подумай, чем его лечат.
- BFF — это слой, а не свалка: бизнес-правил здесь быть не должно, только сборка
  и то, что положено границе.
